# 플레이테스트 키트 — No Handover 1화 「금요일 18:02의 작은 변경」

목표: 보고서 §4의 "1주 프로토타입이 증명해야 할 것" 6문항과 힌트 사다리 속도를 5명(비전공자 3 + 주니어 엔지니어 2)으로 확인한다. 한 명당 약 70분(사전 퀴즈 5분, 플레이 최대 45분, 인터뷰·사후 퀴즈 15분). 다음 날 "기억나는 인물" 질문 1개.

## 준비

- `npm run build && npm run preview` 후 참가자마다 새 창에서 `http://localhost:4173/?fresh=1` (대기 넛지 기본 10분. 다른 값을 시험할 때만 `&nudge=5`).
- 진행자는 화면 녹화(또는 옆자리 관찰)와 이 문서의 결과표를 준비한다.
- 플레이가 끝나면 작업 표시줄 📋 → **플레이 로그 JSON 저장**. 파일 이름에 참가자 번호를 붙인다(P1~P5). 로그는 어디에도 전송되지 않는다.

## 사전·사후 퀴즈 (5문항, 각 1점)

플레이 전과 후에 같은 종이로. 정답은 진행자만 본다.

1. 리눅스에서 "too many open files" 오류는 무엇이 한도에 닿았다는 뜻인가?
   (a) 디스크 용량 (b) 한 프로세스가 열 수 있는 파일 디스크립터 수 (c) 메모리 (d) 동시에 로그인한 사용자 수
2. 다음 중 TCP 연결(소켓)에 대한 설명으로 맞는 것은?
   (a) 파일과 상관없다 (b) 프로세스 입장에서는 열린 파일 하나로 센다 (c) 디스크에 저장된다 (d) root만 만들 수 있다
3. crontab 줄 `15 3 * * 6 /home/u/backup.sh` 는 언제 실행되나?
   (a) 매일 15시 3분 (b) 매주 토요일 03:15 (c) 매월 15일 03:06 (d) 6시간마다
4. 이미 떠 있는 서비스의 "열 수 있는 파일 수" 한도를 확인하는 명령으로 가장 알맞은 것은?
   (a) `ulimit -n` (b) `df -h` (c) `systemctl show <서비스> -p LimitNOFILE` (d) `free -h`
5. `git log --format=fuller` 가 기본 `git log` 보다 더 보여 주는 것은?
   (a) 바뀐 파일 내용 (b) 작성 시각과 반영(커밋) 시각, 작성자와 커미터를 따로 (c) 브랜치 그래프 (d) 리뷰어 승인 여부

정답: 1-b, 2-b, 3-b, 4-c, 5-b. (4번에서 (a)를 고르면 "셸 자신의 한도"와 "서비스 한도"를 구분하지 못한 것이다. 해설 카드의 핵심 포인트.)

## 진행자 대본 (10줄)

1. "오늘 하실 건 게임 테스트예요. 게임을 평가하는 거지 여러분을 평가하는 게 아니에요."
2. "먼저 5문항 퀴즈를 풀어 주세요. 몰라도 괜찮아요. 찍어도 돼요." (5분)
3. "당신은 입사 3주차 신입이고, 지난 금요일에 퇴사한 선배의 PC를 넘겨받았어요. CTO가 오늘 21시까지 토요일 새벽 장애의 원인 보고서를 원해요."
4. "PC 안의 메신저, 메일, 메모장, 터미널을 마음대로 보세요. 터미널이 처음이면 `help` 라고 쳐 보세요."
5. "생각나는 걸 소리 내어 말해 주시면 큰 도움이 돼요. '이거 뭐지', '이 사람 수상한데' 같은 것도요."
6. "저는 옆에서 보기만 하고 정답은 알려 드리지 않아요. 질문하시면 'PC 안에서 찾아보세요'라고만 할 거예요."
7. "💡 힌트 버튼은 이번 테스트에서는 누르지 말아 주세요. 정말 더 못 하겠으면 말씀해 주시고, 그때 눌러도 돼요."
8. "보고서는 세 번까지 낼 수 있어요. 45분이 지나면 그때까지 생각한 걸로 제출해 주세요." (45분 타이머 시작)
9. (끝나면) "결말이 어땠어요? 아하였나요, 속은 느낌이었나요? 가장 막혔던 순간은 언제였어요?" 그리고 사후 퀴즈.
10. "내일 메시지로 질문 하나만 드릴게요. 고맙습니다." (📋 → 로그 JSON 저장, 파일명에 P번호)
